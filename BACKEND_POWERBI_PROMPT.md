# Промпт для агента, который дорабатывает бэкенд: витрина продаж для Power BI

> Отдай этот файл агенту, работающему в репозитории бэкенда (`Avatariya Big data API`,
> Django + DRF). Фронтенд кабинета арендодателя трогать не нужно — он уже готов
> и к этой задаче отношения не имеет.

---

## Задача

Сделать HTTP-эндпоинт, из которого Power BI будет забирать продажи арендодателей
(Аквагрим, Фото, VR и прочие услуги) для отчётности.

Существующий `/api/v1/sales/` для этого **не подходит** и переделывать его не надо —
он решает другую задачу (см. «Почему нельзя переиспользовать /api/v1/sales/»).
Нужен отдельный read-only эндпоинт-витрина.

---

## Почему это делается на бэкенде

Power BI ходит на HTTP-адрес сам, из своего процесса: он не выполняет JavaScript,
не проходит форму логина и не читает токен из `localStorage`. Фронтенд-приложение
он использовать не может в принципе. Поэтому вся работа — на стороне API.

---

## Что уже есть в системе

Проверено на локальном стенде, опираться можно на это:

| Что | Где |
|---|---|
| Продажи арендодателей | модель `Sale`, эндпоинты `/api/v1/sales/`, `/api/v1/sales/totals/`, `/api/v1/sales/scope/` |
| Права арендодателей | модель `SaleUser`, админка `/admin/big_data_app/saleuser/` |
| Парки | модель `Park` (`park_name`, `active`, `guid_1c`, …) |
| Города | модель `City` (`name_ru`, `name_kz`, **`country`** — FK, nullable) |
| Услуги | модель `Product` (приходит из 1С) |
| Аутентификация продаж | `POST /api/v1/sales-auth/token/`, дальше `Authorization: Bearer <token>` |
| Схема API | `GET /openapi-schema`, Swagger — `/docs/` |

Текущая форма записи о продаже (`Sale`): `id`, `user_id`, `username`,
`user_full_name`, вложенный `park` (`id`, `park_name`, `city_id`, `city_name`),
вложенный `product` (`id`, `name`), `price`, `count`, `sale_sum`, `date`,
`created_at`, `updated_at`.

---

## Почему нельзя переиспользовать `/api/v1/sales/`

Четыре причины, каждая ломает Power BI:

1. **Он отдаёт только свои продажи.** Выдача урезана областью доступа
   `SaleUser` — парки и услуги конкретного пользователя. Для отчётности нужны
   продажи всех арендодателей по всем паркам.
2. **Данные вложенные.** `park` и `product` — объекты внутри записи. Power BI это
   разворачивает вручную, и любое изменение структуры ломает отчёт.
3. **Пагинация по 50 записей.** Чтобы забрать год данных, Power BI пришлось бы
   крутить цикл на сотни запросов.
4. **Нет валюты.** Это главное — см. следующий раздел.

---

## Валюта: самое важное в задаче

**Сейчас валюты в API нет вообще.** Фронтенд определяет её сам, по названию
города парка: Ташкент и другие узбекские города → сум, остальные → тенге. Это
костыль, и в Power BI он неповторим — там просто сложатся тенге с сумами в одну
цифру, и отчёт будет молча врать.

В базе для честного решения всё есть: `Park → City → City.country`. Плюс в
модуле кэшбэка уже есть механизм с параметром `display_country=UZ` и кэшированным
курсом — посмотри, как это сделано там, и переиспользуй подход, если он подходит.

**Требование: витрина обязана отдавать поле `currency_code` (`KZT` / `UZS`),
вычисленное на бэкенде по стране города парка.** Никаких догадок по названию
города на стороне потребителя.

Если у части городов `country` не заполнен — не молчи:
- отдавай `currency_code = null` (не подставляй KZT «на всякий случай»);
- предусмотри способ увидеть такие парки, чтобы справочник дозаполнили.

Пересчёт в одну валюту делать **не нужно** — Power BI должен видеть исходные
суммы и код валюты, а конвертацию (если понадобится) построят в отчёте.

## Что реализовать

### 1. Основная витрина

```
GET /api/v1/analytics/sales/
```

Плоская таблица, **одна строка = одна продажа**, без вложенных объектов.

| Поле | Тип | Описание |
|---|---|---|
| `sale_id` | integer | ID записи |
| `date` | string `YYYY-MM-DD` | Дата, за которую зафиксирована продажа |
| `park_id` | integer | |
| `park_name` | string | |
| `city_id` | integer, nullable | |
| `city_name` | string, nullable | |
| `country_id` | integer, nullable | из `City.country` |
| `country_code` | string, nullable | `KZ` / `UZ` |
| `currency_code` | string, nullable | `KZT` / `UZS` — см. раздел про валюту |
| `product_id` | integer | ID услуги из `Product` |
| `product_name` | string | |
| `user_id` | integer | Кто внёс запись |
| `username` | string | |
| `user_full_name` | string | |
| `price` | **number** | Цена за единицу |
| `count` | integer | Количество |
| `sale_sum` | **number** | `price × count`, как посчитал сервер |
| `created_at` | string ISO 8601 со смещением | `2026-09-08T10:15:00+05:00` |
| `updated_at` | string ISO 8601 со смещением | |

**`price` и `sale_sum` — числа, а не строки.** DRF по умолчанию сериализует
`DecimalField` в строку (`"3000.00"`); в Power BI это приезжает текстом, и
суммирование либо падает, либо молча даёт ноль в зависимости от локали.
Поставь `COERCE_DECIMAL_TO_STRING = False` для этого сериализатора.

Параметры запроса (все необязательные):

| Параметр | Описание |
|---|---|
| `date_from`, `date_to` | Границы периода по полю `date`, включительно |
| `updated_from` | Только записи с `updated_at >= значения` — для инкрементального обновления |
| `park`, `product`, `user` | Фильтры по id |
| `format` | `json` (по умолчанию) или `csv` |

### 2. Формат CSV

Поддержи `?format=csv` — для больших выгрузок это заметно быстрее и легче, чем
JSON: Power BI разбирает CSV нативно, а JSON на десятках тысяч строк парсит в M
ощутимо дольше.

Требования к CSV:
- кодировка **UTF-8 с BOM** (иначе Excel и часть версий Power BI ломают кириллицу);
- разделитель — запятая, десятичный разделитель — **точка** (`15000.50`), чтобы
  выгрузка не зависела от локали машины;
- первая строка — заголовки, ровно те же имена полей, что в JSON;
- даты в ISO (`2026-09-08`), без локальных форматов.

### 3. Пагинация

Стандартная пагинация DRF по 50 записей здесь не годится. Сделай так:

- **по умолчанию пагинации нет** — эндпоинт отдаёт всю выборку по фильтрам;
- есть `limit` и `offset` на случай, если понадобится дробить;
- есть защитный предел (например, 200 000 строк на ответ): при превышении —
  `400` с внятным текстом «сузьте период», а не молча обрезанная выдача.
  Молчаливое обрезание — худший вариант: отчёт покажет неполные данные и никто
  этого не заметит.

Оценка объёма: продажи агрегированы по дню, комбинация
*пользователь + парк + услуга + дата* уникальна. Даже при 20 парках и 10 услугах
это порядка 70 000 строк в год — полная выгрузка за год проходит одним запросом.

### 4. Справочники (опционально, но желательно)

Чтобы в Power BI можно было собрать нормальную звезду вместо одной плоской
таблицы:

```
GET /api/v1/analytics/parks/      -> park_id, park_name, city_id, city_name, country_id, country_code, currency_code, active
GET /api/v1/analytics/products/   -> product_id, product_name
GET /api/v1/analytics/users/      -> user_id, username, full_name
```

Если времени мало — сделай сначала основную витрину, справочники потом.

## Аутентификация

Заведи **отдельную сервисную учётку** для Power BI. Не переиспользуй аккаунт
живого арендодателя: у него урезанная область доступа, и при его увольнении
отчётность встанет.

Требования:
- у сервисной учётки доступ **ко всем** паркам и услугам, в обход `SaleUser`;
- доступ строго **read-only**: на этих адресах разрешён только `GET`,
  `POST`/`PATCH`/`DELETE` — `405`;
- токен долгоживущий (Power BI обновляет данные по расписанию без участия
  человека).

Поддержи **два способа** передачи учётных данных:

1. `Authorization: Bearer <token>` — как в остальном API.
2. **HTTP Basic** — Power BI Service поддерживает его нативно в настройках
   источника, и это самый беспроблемный путь для обновления по расписанию.

Почему два: в Power BI Desktop заголовок задаётся вручную в M-коде, а в облачном
Power BI Service такой источник часто отказывается обновляться по расписанию.
Basic снимает этот класс проблем целиком.

Токен в query-параметре (`?token=...`) **не делай**: он попадёт в логи nginx, в
историю браузера и в сохранённый `.pbix`.

---

## Особенности Power BI, которые влияют на реализацию

Это не придирки, а вещи, из-за которых интеграция потом не заводится:

1. **Фильтры — только query-параметрами, не сегментами пути.**
   Power BI собирает запрос так:
   ```
   Web.Contents(BaseUrl, [RelativePath="api/v1/analytics/sales/",
                          Query=[date_from="2026-01-01", date_to="2026-12-31"]])
   ```
   При такой форме базовый адрес остаётся статическим, и обновление по
   расписанию работает. Если период пришлось бы зашивать в путь
   (`/analytics/sales/2026-01-01/2026-12-31/`), источник станет «динамическим»
   и Power BI Service откажется его обновлять.

2. **Стабильные имена полей.** Переименование колонки ломает все построенные
   отчёты. Считай схему витрины публичным контрактом: добавлять поля можно,
   переименовывать и удалять — нет.

3. **`null` вместо пропущенного ключа.** Если у парка нет города, поле должно
   присутствовать со значением `null`, а не исчезать из объекта — иначе Power BI
   в одних строках видит колонку, в других нет, и тип определяется неверно.

4. **Смещение времени в `created_at`/`updated_at` сохраняй** (`+05:00`).
   Без него Power BI решит, что это UTC, и сдвинет время на 5 часов.

5. **Таймаут.** Ответ должен укладываться в разумное время; выгрузка за год не
   должна упираться в таймаут gunicorn/nginx. Проверь на реальном объёме.

---

## Производительность

- `select_related('park', 'park__city', 'product', 'user')` — иначе на каждой
  строке будет отдельный запрос за парком и услугой.
- Индексы по `date`, и составной по (`park`, `product`, `date`) — под фильтры.
- Для CSV отдавай ответ потоково (`StreamingHttpResponse`), чтобы не держать
  всю выгрузку в памяти.
- `.values()` / `.iterator()` вместо материализации объектов модели, если строк
  много.

---

## Про удаление записей

Если арендодатель удалил продажу, при полном обновлении Power BI это увидит —
строка просто исчезнет. А вот при инкрементальном обновлении (по `updated_from`)
удаление невидимо: запись останется в отчёте навсегда.

Поэтому:
- при текущем объёме данных **достаточно полного обновления**, инкрементальное
  городить не нужно;
- если позже понадобится — сделай мягкое удаление (`deleted_at`) и отдавай
  удалённые записи с флагом, а не выкидывай их из выдачи.

Инкрементальное обновление стоит делать только когда полная выгрузка перестанет
укладываться в таймаут — не раньше.

## Как проверить, что готово

```bash
# 1. токен сервисной учётки
curl -X POST http://localhost:8000/api/v1/sales-auth/token/ \
  -H "Content-Type: application/json" \
  -d '{"username":"powerbi_service","password":"..."}'

# 2. витрина за период
curl "http://localhost:8000/api/v1/analytics/sales/?date_from=2026-09-01&date_to=2026-09-30" \
  -H "Authorization: Bearer <token>"

# 3. то же через Basic
curl "http://localhost:8000/api/v1/analytics/sales/?date_from=2026-09-01&date_to=2026-09-30" \
  -u powerbi_service:...

# 4. CSV
curl "http://localhost:8000/api/v1/analytics/sales/?format=csv&date_from=2026-09-01" \
  -H "Authorization: Bearer <token>" -o sales.csv

# 5. только GET
curl -X POST "http://localhost:8000/api/v1/analytics/sales/" \
  -H "Authorization: Bearer <token>"   # ожидается 405
```

Проверка со стороны Power BI (Получить данные → Пустой запрос → Расширенный редактор):

```m
let
    Source = Json.Document(
        Web.Contents(
            "http://localhost:8000",
            [
                RelativePath = "api/v1/analytics/sales/",
                Query = [date_from = "2026-09-01", date_to = "2026-09-30"],
                Headers = [#"Authorization" = "Bearer " & Token]
            ]
        )
    ),
    Table = Table.FromRecords(Source)
in
    Table
```

### Чек-лист приёмки

- [ ] Выдача плоская, вложенных объектов нет
- [ ] `price` и `sale_sum` — числа, не строки
- [ ] `currency_code` заполнен и вычислен по стране города, а не по названию
- [ ] Города без `country` дают `currency_code = null`, а не подставленный KZT
- [ ] Видны продажи **всех** арендодателей, а не одной учётки
- [ ] `POST`/`PATCH`/`DELETE` возвращают `405`
- [ ] Работают и Bearer, и Basic
- [ ] `?format=csv` отдаёт UTF-8 с BOM и точкой как десятичным разделителем
- [ ] Фильтры принимаются query-параметрами
- [ ] Выгрузка за год проходит одним запросом и укладывается в таймаут
- [ ] Превышение предела строк даёт `400` с текстом, а не обрезанную выдачу
- [ ] Эндпоинты попали в `/openapi-schema` и видны в Swagger

## Альтернатива, если Power BI работает внутри сети

Если отчёты строятся внутри периметра, где виден Postgres, можно не делать API
вообще: у Power BI есть родной коннектор к PostgreSQL, включая DirectQuery.
Тогда вместо эндпоинта достаточно **read-only представления** в базе с той же
структурой полей, что описана выше, и отдельной учётки БД с правом `SELECT`
только на это представление.

Это меньше кода и быстрее работает на больших объёмах. Минусы: БД придётся
открыть для машин с Power BI, и снаружи периметра (или из Power BI Service без
шлюза) такой источник недоступен.

**Что бы ни выбрали — логика валюты остаётся на сервере**, в представлении или в
сериализаторе. Ни в коем случае не в отчёте Power BI: как только правило
продублируется на стороне BI, две копии разъедутся.

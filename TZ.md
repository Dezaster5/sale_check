ТЗ: Интерфейс фиксации продаж арендодателей — Аквагрим, Фото, VR
1. Цель
Разработать сервис для фиксации и последующего анализа продаж арендодателей по услугам Аквагрим, Фото, VR и другим услугам, заведенным в системе.
Сервис должен позволять получать аналитику по:
паркам;
арендодателям/пользователям;
услугам;
датам и периодам;
количеству продаж;
цене;
общей сумме продаж.
Этапы разработки
Этап 1. Арендодатель фиксирует итоговые продажи за день по каждой услуге: количество, цена и общая сумма.

2. Веб-интерфейс
Необходимо разработать веб-интерфейс, доступный после авторизации пользователя.

2.1. Вкладка «Продажи»
Вкладка предназначена для внесения продаж.
Поля:
Поле
Описание
Дата продажи
По умолчанию текущая дата. Возможность выбора другой даты определяется правами пользователя
Парк
Если пользователю доступен один парк — устанавливается автоматически. Если несколько — выбор из доступного списка
Услуга
Если пользователю доступна одна услуга — устанавливается автоматически. Если несколько — выбор из доступного списка
Количество
Целое положительное число
Цена
Цена за единицу услуги
Стоимость
Рассчитывается автоматически: Количество × Цена

Кнопка «Сохранить» создаёт запись о продаже.
Ограничения
Пользователь должен видеть и иметь возможность выбирать только те парки и услуги, которые назначены ему администратором.
По умолчанию пользователь может заводить продажи только за текущую дату.
В зависимости от назначенных прав пользователь дополнительно может:
создавать продажи за прошедшие даты;
редактировать ранее созданные продажи;
удалять продажи;
изменять дату продажи.
Необходимо исключить возможность случайного дублирования одной и той же дневной продажи. Если по комбинации пользователь + парк + услуга + дата запись уже существует, система должна либо предложить отредактировать существующую запись, либо явно предупредить пользователя о наличии продажи за эту дату.

Пользователь должен иметь возможность просматривать ранее внесённые продажи в рамках доступных ему парков и услуг.

Доступность кнопок «Редактировать» и «Удалить» определяется правами пользователя.

4. Авторизация
Авторизация выполняется по логину и паролю.
Учетные записи создаются администратором сервиса.
Для каждого пользователя администратор определяет:
доступные парки;
доступные услуги;
функциональные права.
Самостоятельная регистрация пользователей не требуется.

5. Права доступа
Настройка прав выполняется через Django Admin.
Для пользователя необходимо иметь возможность назначить:
Область доступа:
один или несколько парков;
одну или несколько услуг (product_id).
Функциональные права:
создание продажи за текущую дату;
создание продажи за прошлую дату;
изменение даты продажи;
редактирование продажи;
удаление продажи.
Пользователь не должен иметь возможности получить через интерфейс или API доступ к продажам, паркам и услугам, которые ему не назначены.

6. Интеграция с BigData / 1С
Товары/услуги создаются в 1С и передаются в BigData.
Источник услуг — существующая таблица Product.
В новом сервисе повторно создавать справочник услуг не требуется.
Для связи используется:
Product.product_id
Пользователь получает доступ только к тем product_id, которые назначены ему администратором.

7. Структура данных
7.1. sale_user
Таблица/модель для настройки доступа пользователя.
Необходимо предусмотреть:
user — пользователь;
связь с одним или несколькими product_id;
связь с одним или несколькими парками;
can_create_past_sales — возможность создавать продажи за прошлые даты;
can_change_sale_date — возможность изменять дату;
can_edit_sales — возможность редактирования;
can_delete_sales — возможность удаления.
Настройка выполняется через Django Admin.
Если одному пользователю может быть назначено несколько парков и несколько услуг, для этих связей корректнее использовать ManyToMany, а не один ForeignKey.

user_id должен обозначать именно пользователя, создавшего запись о продаже, а не пользователя, создавшего Product, поскольку сам Product поступает из 1С.
Расчёт:
sale_sum = price × count
Расчёт должен выполняться системой, а не вводиться пользователем вручную.

8. Валидация
При сохранении необходимо проверять:
count > 0;
price >= 0;
выбранный парк доступен пользователю;
выбранная услуга доступна пользователю;
пользователь имеет право создавать продажу на выбранную дату;
пользователь имеет соответствующие права при редактировании/удалении.
Проверки должны выполняться на backend, а не только ограничением элементов интерфейса.

# Avatariya — кабинет арендодателя (фронтенд)

Веб-интерфейс фиксации продаж арендодателей: внесение дневных продаж по услуге
и парку и просмотр истории с итогами за период.

Бэкенд (Django + DRF) живёт отдельно и этим приложением не меняется — фронтенд
только ходит в его REST API.

## Запуск

```bash
npm install
npm run dev:remote      # против тестового сервера
```

Приложение поднимется на http://localhost:5173.

| Команда | Против какого бэкенда | Что делает |
|---|---|---|
| `npm run dev` | из `.env` | Дев-сервер, адрес берётся из личного `.env` |
| `npm run dev:remote` | `http://188.94.158.71:8000` | Тестовый сервер |
| `npm run dev:localhost` | `http://localhost:8000` | Локальный бэкенд в Docker |
| `npm run build` | относительный `/api` | Продакшен-сборка в `dist/` (см. «Деплой») |
| `npm run build:remote` | `http://188.94.158.71:8000` | Сборка с прямым обращением к тестовому серверу |
| `npm run preview` | — | Локальный просмотр собранной версии |
| `npm run typecheck` | — | Проверка типов без сборки |

Переключаться между стендами правкой файлов не нужно — достаточно выбрать
команду.

### Учётные записи

На **тестовом сервере** учётных записей пока нет: `sales_demo` существовал
только в локальной базе разработчика, на тестовом стенде вход вернёт 401
с текстом «Неверный логин или пароль». Учётку заводит владелец бэкенда в Django
Admin, там же назначает парки, услуги и права.

Пока аккаунта нет, на тестовом сервере проверяется только экран входа и
обработка ошибок; всё остальное — на локальном бэкенде с `sales_demo` /
`sales_demo_123`.

## Переменные окружения

Vite подхватывает только переменные с префиксом `VITE_`. Готовые наборы лежат
в репозитории, личные значения можно положить в `.env` (он в `.gitignore`).

| Файл | Когда применяется |
|---|---|
| `.env.remote` | `npm run dev:remote`, `npm run build:remote` |
| `.env.localhost` | `npm run dev:localhost` |
| `.env.production` | `npm run build` |
| `.env` | `npm run dev` — личные настройки, в git не попадает |
| `.env.example` | шаблон с пояснениями |

| Переменная | Описание |
|---|---|
| `VITE_API_BASE_URL` | Адрес бэкенда **без** `/api/v1` на конце. Путь `/api/v1` клиент дописывает сам. **Пустая строка** = запросы уходят на тот же адрес, откуда отдан фронтенд (вариант с прокси, см. «Деплой») |
| `VITE_UZ_CITY_IDS` | Необязательная. Id городов Узбекистана через запятую, например `7,12`. Нужна, пока в справочнике парков не заполнен `city_name` — см. «Итоги и валюта» |

Значения `VITE_*` **вшиваются в бандл на этапе сборки**, а не читаются в
рантайме: чтобы сменить адрес бэкенда у собранного приложения, нужна
пересборка (или вариант с прокси, где адрес вообще не вшивается).

## Стек

React 18 + TypeScript + Vite, серверное состояние на TanStack Query, стили —
CSS-модули поверх общих токенов брендбука (`src/styles/tokens.css`).

Роутер не подключён намеренно: экрана всего два и оба за логином, состояние
вкладки живёт в React-состоянии. Если позже понадобятся ссылки на конкретный
фильтр истории, добавить `react-router` будет дешевле, чем разбирать его сейчас.

## Структура

```
src/
  api/        клиент, типы, разбор ошибок DRF, хуки TanStack Query
  auth/       контекст авторизации и экран входа
  components/ layout, модалка, тосты, скелетоны, общие стили
  lib/        валюта, форматирование, палитра брендбука
  pages/      вкладки «Продажи» и «История продаж», модалка правки
```

## Как это работает

### Авторизация

`POST /sales-auth/token/` → токен в `localStorage`, дальше он уходит в заголовке
`Authorization: Bearer <token>`. Токен по времени не истекает, поэтому сессия
переживает перезагрузку. Любой ответ **401** чистит сессию и возвращает на экран
входа. 401 и 403 на входе показываются разным текстом: неверный пароль против
«доступ к сервису не настроен».

Регистрации нет — учётные записи заводит администратор в Django Admin.

### Область доступа

Сразу после входа запрашивается `GET /sales/scope/`. Из него берутся списки
парков и услуг, права и — важно — **дата «сегодня»**. Браузерный `new Date()`
не используется нигде: у планшета в парке может быть свой часовой пояс или
сбитые часы, а бэкенд считает день по времени парков (UTC+5).

Права из `permissions` только прячут элементы интерфейса. Бэкенд проверяет всё
повторно, и его 403 обрабатывается наравне с остальными ошибками.

### Итоги и валюта

Итоги за период берутся из `GET /sales/totals/` с теми же фильтрами, что и
список — строки таблицы на клиенте не суммируются, иначе при пагинации итог
будет неверным.

Валюту бэкенд не отдаёт, она выводится из города парка
(`src/lib/currency.ts`): города Узбекистана → сум (`сўм`), остальные → тенге
(`₸`). Город может прийти пустым или `null` — тогда берётся тенге по умолчанию,
интерфейс при этом не ломается.

Если в выборку попали парки разных стран, итоги показываются **раздельно по
каждой валюте**. Здесь есть тонкость: `/totals/` отдаёт одну сумму на запрос, а
параметр `park` не повторяемый — при `park=9&park=1` бэкенд берёт последний.
Поэтому в мультивалютном случае итоги собираются отдельным запросом на каждый
парк и группируются по валюте; складываются при этом серверные итоги, а не
строки таблицы. Обычный одновалютный случай остаётся одним запросом.

### Выгрузка в Excel

Кнопка «Выгрузить в Excel» на вкладке истории собирает `.xlsx` по **текущим
фильтрам целиком**, а не по открытой странице: клиент проходит все страницы
`GET /sales/` и складывает их в один лист.

В листе шапка с периодом и фильтрами, таблица с автофильтром и закреплённой
шапкой, а внизу — итоги отдельной строкой на каждую валюту. Количество, цена и
сумма записываются числами с денежным форматом, поэтому в Excel их сразу можно
складывать и строить сводные таблицы. Валюта вынесена отдельной колонкой —
складывать тенге с сумами нельзя и здесь.

Библиотека `exceljs` весит около мегабайта и подключается динамическим
`import()` — она попадает в отдельный чанк и грузится только при первом нажатии
на кнопку, не утяжеляя вход в приложение.

### Раскладка на телефоне

Ниже 900px интерфейс перестраивается, а не просто сужается: боковая панель
занимала треть экрана по вертикали, и до первой записи в истории приходилось
пролистывать больше экрана.

- шапка сжимается в строку 60px: логотип, имя пользователя, «Выйти»;
- вкладки уезжают в нижнюю навигацию — их две, и на телефоне им место под
  большим пальцем;
- крупная цифра раздела и строка «Avatariya · Кабинет арендодателя» скрываются;
- фильтры истории сворачиваются в строку-сводку («Фильтры · 27.08 — 09.09») и
  раскрываются по нажатию, даты внутри встают в две колонки;
- таблица истории уступает место карточкам;
- диалоги показываются шторкой снизу во всю ширину, кнопки — в половину каждая;
- у всего нажимаемого высота не меньше 44–48px.

Обе раскладки живут в одном дереве, и `<main>` стоит на одной позиции в обеих.
Это важно: планшет в портрете (768px) получает мобильную раскладку, в альбоме
(1024px) — десктопную, и при повороте React не должен размонтировать содержимое,
иначе наполовину заполненная форма продажи потеряется.

### Дубли продаж

Одна продажа = одна комбинация *пользователь + парк + услуга + дата*. При
попытке завести вторую бэкенд отвечает **409** и кладёт в тело полный объект
существующей записи. Интерфейс показывает модалку с её данными и кнопкой
«Редактировать существующую» — повторный запрос за записью не делается.
Кнопка появляется только при праве `can_edit_sales`.

### Редактирование

Правка открывается модалкой поверх текущей вкладки — и из истории, и из
конфликта 409. Так не теряется контекст: после правки пользователь остаётся
там, где был. Поле даты доступно только при `can_change_sale_date`. В PATCH
уходят только изменившиеся поля.

## Деплой

### Главная засада: бэкенд работает без TLS

Тестовый сервер доступен только по `http://188.94.158.71:8000` — на `https://`
он не отвечает. Если отдать фронтенд по HTTPS и обращаться к API напрямую,
браузер заблокирует все запросы как mixed content, и приложение молча перестанет
работать. Поэтому предусмотрены два варианта, и по умолчанию собран **первый**.

### Вариант 1 (по умолчанию): фронтенд проксирует API

`npm run build` собирает бандл с **пустым** `VITE_API_BASE_URL`. Запросы уходят
на тот же адрес, откуда отдан фронтенд (`/api/v1/...`), а nginx фронтенда
проксирует их на бэкенд уже со стороны сервера.

Это снимает сразу три проблемы:

- **mixed content** — запрос к http-бэкенду делает сервер, а не браузер, поэтому
  страницу можно спокойно отдавать по HTTPS;
- **CORS** — для браузера это то же происхождение, предварительный запрос не нужен вовсе;
- **смена адреса бэкенда** не требует пересборки фронтенда: адрес живёт в
  переменной `API_UPSTREAM` у контейнера.

```bash
docker compose up -d --build      # соберёт и поднимет на http://localhost:8080
```

Адрес бэкенда меняется переменной окружения контейнера:

```yaml
environment:
  API_UPSTREAM: http://188.94.158.71:8000
```

Без Docker: соберите `npm run build`, положите `dist/` в корень статики nginx и
возьмите конфиг из `nginx.conf.template`, подставив в нём `${API_UPSTREAM}`.

### Вариант 2: прямое обращение к API

Годится, только если фронтенд тоже отдаётся **по http** — иначе см. mixed content.

```bash
npm run build:remote
```

Адрес бэкенда вшивается в бандл, `/api` проксировать не нужно. CORS на тестовом
сервере уже настроен и отражает любой Origin, так что домен фронтенда в белый
список добавлять не придётся.

### Когда у бэкенда появится TLS

Оба варианта продолжат работать. Вариант 1 останется предпочтительным: он не
требует пересборки при смене адреса и не зависит от настроек CORS.

### Проверка перед выкатом

```bash
npm run typecheck
npm run build
docker compose up -d --build
curl -s -o /dev/null -w "%{http_code}
" http://localhost:8080/            # 200
curl -s -o /dev/null -w "%{http_code}
" http://localhost:8080/api/v1/sales/  # 401 — прокси дошёл до бэкенда
```

`401` на втором запросе — правильный результат: значит nginx достучался до
бэкенда, а тот отверг запрос без токена.

## Известные ограничения

- **Города.** На локальном стенде `city_name` приходит пустой строкой (справочник
  городов заполнили позже даты дампа), поэтому все парки показываются в тенге.
  Проверить узбекский кейс локально можно, проставив городу название «Ташкент»
  на бэкенде либо указав его id в `VITE_UZ_CITY_IDS`. На проде, где справочник
  заполнен, определение по названию работает само.
- **Валюта — эвристика.** Бэкенд не отдаёт ни валюту, ни страну, поэтому список
  узбекских городов зашит на фронтенде. Новый парк в городе, которого нет в
  списке, молча покажется в тенге. Надёжнее было бы поле `country` или
  `currency` в API.
- **Нет учётки на тестовом сервере.** Полный сценарий (внесение, история,
  выгрузка) там пока не проверить — нужен аккаунт от владельца бэкенда.
- **HTTP без шифрования.** Пока у бэкенда нет TLS, логин и токен ходят по сети
  открытым текстом. Для внутренней панели за логином это заметный риск, который
  закрывается только со стороны бэкенда.
- **Сортировка.** Список всегда запрашивается с `ordering=-date`. Сортировка по
  клику на заголовок не сделана — API её поддерживает, добавляется дёшево.
- **Объём выгрузки.** Экспорт тянет страницы последовательно, с ограничением в
  200 страниц (около 10 000 записей). Для больших периодов это заметное число
  запросов — если выгрузки станут регулярными, дешевле добавить на бэкенде
  отдельный эндпоинт, отдающий файл одним ответом.

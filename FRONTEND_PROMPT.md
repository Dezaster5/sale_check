## Задача

Напиши веб-интерфейс фиксации продаж арендодателей для сети парков Avatariya
(услуги: Аквагрим, Фото, VR и другие, заведённые в 1С).

Бэкенд — Django + DRF, уже реализован и задеплоен, трогать его нельзя.
Твоя работа — только фронтенд, отдельным приложением, которое ходит в REST API.

В корне репозитория лежит `sales-mvp-avatariya.html` — статический прототип на
одном файле с моковыми данными. Это ориентир по внешнему виду и составу
экранов, но **не эталон**: часть логики в нём упрощена или расходится с
финальными требованиями. Ниже перечислено, что именно нужно поправить.

## Стек

Выбери сам, но по умолчанию: **React + TypeScript + Vite**, состояние на
TanStack Query, стили — Tailwind или CSS-модули. Никакого SSR, это внутренняя
панель за логином. Если считаешь, что другой стек лучше — обоснуй в README.

## Модель предметной области

- **Парк** — физический парк в городе (Алматы, Астана, Ташкент и т.д.).
  В прототипе парки названы «мирами» (Ice World, Water World) — это неверно,
  «мир» это зона внутри парка. Везде пиши **«Парк»**, а не «Мир парка».
- **Услуга** — запись из справочника `Product`. Справочник приходит из 1С,
  фронтенд его не редактирует и не создаёт.
- **Продажа** — итог за день по комбинации *пользователь + парк + услуга + дата*.
  Одна такая комбинация = одна запись. Сумма считается на бэкенде.
- **Область доступа** — администратор в Django Admin назначает пользователю
  список парков и список услуг. Доступны все сочетания: если назначены парки
  A и B и услуги «Аквагрим» и «Фото», доступны все 4 комбинации.

## API

Базовый URL: `{API_BASE}/api/v1/` — вынеси в переменную окружения
(`VITE_API_BASE_URL`), не хардкодь.

### Авторизация

```
POST /api/v1/sales-auth/token/
Content-Type: application/json

{ "username": "ivan", "password": "secret" }
```

**200:**
```json
{ "token": "9c1f...", "user_id": 12, "username": "ivan", "full_name": "Иван Иванов" }
```

- **401** — неверный логин или пароль.
- **403** — пользователь есть, но доступ к сервису продаж не настроен
  (или отключён администратором). Покажи текст из поля `error`.

Дальше все запросы шлют заголовок:
```
Authorization: Bearer <token>
```

Токен не истекает по времени. Храни его в `localStorage`. При любом ответе
**401** — чисти токен и возвращай на экран входа. Регистрации нет: учётные
записи заводит администратор.

### Область доступа и права

```
GET /api/v1/sales/scope/
```

```json
{
  "user_id": 12,
  "username": "ivan",
  "full_name": "Иван Иванов",
  "today": "2026-09-08",
  "parks": [
    { "id": 4, "park_name": "Avatariya Мега Алматы", "city_id": 2, "city_name": "Алматы" },
    { "id": 9, "park_name": "Avatariya Tashkent City", "city_id": 7, "city_name": "Ташкент" }
  ],
  "products": [
    { "id": 58629, "name": "Аквагрим" },
    { "id": 13417, "name": "Аквагрим средний" }
  ],
  "permissions": {
    "can_create_past_sales": false,
    "can_change_sale_date": false,
    "can_edit_sales": true,
    "can_delete_sales": false
  }
}
```

Запрашивай **сразу после входа** и держи в состоянии приложения. По нему:
- заполняются выпадающие списки парков и услуг;
- решается, показывать ли кнопки «Редактировать» / «Удалить»;
- берётся **дата «сегодня»** — используй `today` из ответа, а не
  `new Date()` в браузере. У пользователя может быть другой часовой пояс или
  сбитые часы, а бэкенд считает «сегодня» по времени парков (UTC+5).

### Список продаж

```
GET /api/v1/sales/?date_from=2026-09-01&date_to=2026-09-08&park=4&product=58629&page=1&ordering=-date
```

Все параметры необязательны. Ответ — стандартная пагинация DRF, 50 записей на
страницу:

```json
{
  "count": 137,
  "next": "http://.../api/v1/sales/?page=2",
  "previous": null,
  "results": [
    {
      "id": 42,
      "user_id": 12,
      "username": "ivan",
      "user_full_name": "Иван Иванов",
      "park": { "id": 4, "park_name": "Avatariya Мега Алматы", "city_id": 2, "city_name": "Алматы" },
      "product": { "id": 58629, "name": "Аквагрим" },
      "price": "3000.00",
      "count": 5,
      "sale_sum": "15000.00",
      "date": "2026-09-08",
      "created_at": "2026-09-08T10:15:00+05:00",
      "updated_at": "2026-09-08T10:15:00+05:00"
    }
  ]
}
```

`ordering` принимает `date`, `sale_sum`, `count`, `id` (с `-` для убывания).
По умолчанию `-date`.

Пользователь всегда получает **только свои** продажи и только по назначенным
ему паркам и услугам — фильтровать на клиенте по пользователю не нужно.

### Итоги за период

```
GET /api/v1/sales/totals/?date_from=...&date_to=...&park=...&product=...
```

```json
{ "total_count": 137, "total_sum": "421000.00", "records": 29 }
```

Принимает **те же фильтры**, что и список. Считается по всей выборке, а не по
текущей странице — не суммируй строки на клиенте, это даст неверный итог при
пагинации. Вызывай этот эндпоинт с теми же параметрами, что и список.

### Создание продажи

```
POST /api/v1/sales/
{ "park_id": 4, "product_id": 58629, "price": "3000.00", "count": 5, "date": "2026-09-08" }
```

`date` можно не передавать — тогда бэкенд подставит текущую дату.
`sale_sum` передавать не нужно: поле только на чтение, значение из запроса
игнорируется, сумма всегда считается как `price × count` на сервере.

**201** — созданная запись в формате из списка выше.

**409 Conflict** — продажа за эту дату по этой комбинации уже есть:
```json
{
  "error": "Продажа по этой услуге, парку и дате уже существует",
  "existing_sale_id": 42,
  "existing_sale": { ...полный объект продажи... }
}
```
Обработай это отдельно: покажи модалку «Продажа за эту дату уже внесена:
5 шт × 3000 ₸» с кнопками «Редактировать существующую» и «Отмена». Данные для
модалки бери из `existing_sale`, повторный запрос делать не надо. В прототипе
такая модалка уже нарисована.

### Изменение и удаление

```
PATCH  /api/v1/sales/{id}/     { "count": 7 }
DELETE /api/v1/sales/{id}/
```

`PATCH` принимает любое подмножество полей `park_id`, `product_id`, `price`,
`count`, `date`. Сумма пересчитывается сервером. Ответ **200** с обновлённой
записью, при конфликте дат — снова **409**.

`DELETE` возвращает **204** без тела.

### Коды ошибок

| Код | Когда | Что делать |
|-----|-------|-----------|
| 400 | Невалидные данные | Показать ошибки под полями. Формат DRF: `{"field": ["текст"]}` или `{"detail": "текст"}` |
| 401 | Нет/протух токен | Очистить токен, вернуть на экран входа |
| 403 | Нет права на операцию, либо парк/услуга вне области доступа | Показать текст из `detail` |
| 404 | Чужая или несуществующая запись | «Запись не найдена» |
| 409 | Дубль продажи | Модалка «Редактировать существующую» |

Не полагайся на то, что интерфейс не даст сделать запрещённое: бэкенд
проверяет всё повторно и вернёт 403. Обработай это.

## Экраны

### 1. Вход

Логин и пароль. Никакой регистрации и восстановления пароля.
Ошибки 401 и 403 показывай разным текстом — это разные ситуации
(«неверный пароль» против «доступ не настроен, обратитесь к администратору»).

### 2. Вкладка «Продажи» — внесение

| Поле | Поведение |
|------|-----------|
| Дата продажи | По умолчанию `today` из `/scope/`. Если `can_create_past_sales = false` — поле только для чтения, показывай сегодняшнюю дату. Если `true` — datepicker, но **будущие даты заблокированы всем** (`max = today`) |
| Парк | Из `scope.parks`. Если парк один — подставить и не показывать выбор |
| Услуга | Из `scope.products`. Если услуга одна — подставить и не показывать выбор |
| Количество | Целое, > 0 |
| Цена | За единицу, >= 0, дробное с 2 знаками |
| Стоимость | Только для чтения, считается на лету `count × price`. Это превью — итоговое значение всё равно придёт с сервера |

Кнопка «Сохранить продажу». После успеха — очистить форму, показать тост и
обновить историю.

### 3. Вкладка «История продаж»

Фильтры: период «с» / «по», парк, услуга, кнопка сброса.
Таблица: Дата, Парк, Услуга, Количество, Цена, Сумма, Пользователь.
Внизу — итоги за период: «Общее количество: X», «Общая сумма продаж: Y».

Кнопки «Редактировать» и «Удалить» в строке показывай только при
`can_edit_sales` / `can_delete_sales`. Удаление — с подтверждением.

В режиме редактирования поле даты доступно только при `can_change_sale_date`.

## Валюта — важный нюанс

**Бэкенд не отдаёт валюту.** Определяй её на фронтенде по городу парка
(`park.city_name` / `park.city_id` из `/scope/` и из объекта продажи):

- Ташкент и другие города Узбекистана → **сум** (`UZS`), символ `сўм`
- все остальные (Алматы, Астана и т.д.) → **тенге** (`KZT`), символ `₸`

Заведи один модуль-маппер `currencyForCity(cityId | cityName)` и используй его
везде: в форме («Цена, ₸» / «Цена, сўм»), в таблице, в итогах. В прототипе
валюта захардкожена как `₸` — это ошибка, которую нужно исправить.

Итоги за период считай и показывай **раздельно по валютам**, если в выборку
попали парки разных стран. Складывать тенге с сумами нельзя. Проще всего —
если в выборке больше одной валюты, показать две строки итогов; либо не
позволять выбрать в фильтре парки разных стран одновременно. Реши сам, но
молча складывать разные валюты — недопустимо.

Суммы форматируй с разделителями разрядов (`15 000 ₸`). Учти, что суммы в
сумах на два-три порядка больше — колонки в таблице не должны разъезжаться.

## Что исправить относительно прототипа `sales-mvp-avatariya.html`

1. **«Мир парка» → «Парк»** во всех подписях.
2. **Валюта по городу**, а не захардкоженный `₸` (см. выше).
3. **Переключатель пользователей в сайдбаре убрать.** В прототипе это заглушка
   для демонстрации ролей. В реальном приложении пользователь один — тот, кто
   вошёл. Вместо селекта покажи имя пользователя и кнопку «Выйти».
4. **Данные с сервера, а не из констант** `PARKS` / `SERVICES` / `USERS`.
   Списки парков и услуг у каждого пользователя свои.
5. **Итоги — из `/totals/`**, а не суммированием строк на клиенте.
6. **Пагинация** — в прототипе её нет, а записей может быть много.
7. **Обработка 409** — модалка в прототипе есть, но подключи её к реальному
   ответу сервера и покажи в ней данные существующей записи.
8. **Дата «сегодня» — из `/scope/`**, а не `new Date()` в браузере.
9. **Состояния загрузки и ошибок** — в прототипе их нет вообще. Нужны скелетоны
   при загрузке, тосты при ошибках, блокировка кнопки на время запроса
   (чтобы двойной клик не создал дубль).
10. **Пустые состояния** — «Продаж за выбранный период нет».

Фирменные цвета из прототипа (`#0047BB`, `#0072CE`, `#008C15`, `#FF8200`,
`#AE2573`, фиолетовая палитра услуг) сохрани — это брендбук Avatariya.

## Требования к качеству

- Адаптивность: с интерфейсом работают с планшетов и телефонов прямо в парке.
  Таблица истории на узких экранах — карточками либо с горизонтальной прокруткой
  внутри своего контейнера.
- Все суммы и количества — с проверкой на клиенте, но полагаться на неё нельзя,
  ошибки сервера всё равно обрабатывай.
- Не отправляй повторный POST, пока не пришёл ответ на предыдущий.
- Токен в `localStorage`, но не логируй его и не клади в URL.
- README: как запустить, какие переменные окружения нужны, как указать
  адрес бэкенда.

## Чего делать не нужно

- Регистрации, восстановления пароля, редактирования профиля.
- Справочника услуг и парков (они приходят из 1С через бэкенд).
- Админки прав — права настраиваются в Django Admin.
- Отчётов и графиков сверх итогов за период (это следующий этап).

## Локальный стенд

Бэкенд поднят локально в Docker и доступен по адресу:

```
http://localhost:8000
```

Пропиши в `.env` фронтенда:

```
VITE_API_BASE_URL=http://localhost:8000
```

CORS на локальном стенде открыт для всех источников, поэтому Vite на любом
порту (5173 и т.д.) достучится без настройки прокси.

### Адреса эндпоинтов

| Назначение | Метод и адрес |
|---|---|
| Вход, получение токена | `POST http://localhost:8000/api/v1/sales-auth/token/` |
| Область доступа и права | `GET http://localhost:8000/api/v1/sales/scope/` |
| Список продаж | `GET http://localhost:8000/api/v1/sales/` |
| Создание продажи | `POST http://localhost:8000/api/v1/sales/` |
| Изменение продажи | `PATCH http://localhost:8000/api/v1/sales/{id}/` |
| Удаление продажи | `DELETE http://localhost:8000/api/v1/sales/{id}/` |
| Итоги за период | `GET http://localhost:8000/api/v1/sales/totals/` |

Вспомогательное (не для фронтенда, для проверки руками):

| Назначение | Адрес |
|---|---|
| Swagger с полной схемой API | http://localhost:8000/docs/ |
| Django Admin — настройка прав | http://localhost:8000/admin/big_data_app/saleuser/ |

### Демо-аккаунт

```
логин:  sales_demo
пароль: sales_demo_123
```

У него включены все четыре права (правка, удаление, прошлые даты, смена даты),
назначены 3 парка и 3 услуги. Чтобы проверить поведение урезанных прав,
сними галочки в Django Admin или попроси владельца бэкенда завести второй
аккаунт.

### Проверка, что бэкенд отвечает

```bash
curl -X POST http://localhost:8000/api/v1/sales-auth/token/ \
  -H "Content-Type: application/json" \
  -d '{"username":"sales_demo","password":"sales_demo_123"}'
```

Должен вернуться JSON с полем `token`. Дальше:

```bash
curl http://localhost:8000/api/v1/sales/scope/ -H "Authorization: Bearer <token>"
```

### Про данные локальной базы

База восстановлена из дампа продакшена за май 2025. Учти два момента:

1. **`city_name` в ней приходит пустой строкой** — справочник городов заполнили
   позже даты дампа. На проде поле заполнено. Значит определение валюты по
   городу локально не проверить напрямую, и — важнее — **фронтенд обязан
   корректно работать при пустом или `null` городе**: в этом случае показывай
   валюту по умолчанию (тенге) и не роняй интерфейс. Для локальной проверки
   узбекского кейса попроси владельца бэкенда проставить городу название
   «Ташкент», либо временно подмени значение в моке.
2. Названия услуг в справочнике реальные и довольно длинные («Аквагрим ШТ»,
   «Аренда фотобудки»). Выпадающий список и колонка таблицы должны переживать
   длинные названия без разъезжания вёрстки.

# ОБНОВЛЕНИЕ

Контракт API **не менялся** — все эндпоинты, поля и коды ответов выше
актуальны. Переписывать уже написанный код не нужно. Изменилось окружение.

## Появился настоящий тестовый сервер

Бэкенд задеплоен и доступен из интернета:

```
http://188.94.158.71:8000
```

Поднимать локальный бэкенд больше не нужно — работай с этим адресом:

```
VITE_API_BASE_URL=http://188.94.158.71:8000
```

Проверено, что на нём уже развёрнуто и отвечает:

| Адрес | Статус |
|---|---|
| `POST /api/v1/sales-auth/token/` | работает |
| `GET /api/v1/sales/` | работает (401 без токена — как и должно) |
| `GET /api/v1/sales/scope/` | работает |
| `GET /api/v1/sales/totals/` | работает |
| Swagger со схемой | http://188.94.158.71:8000/docs/ |

**CORS уже настроен под Vite.** Сервер отвечает на preflight с
`Origin: http://localhost:5173` и разрешает заголовок `authorization`,
методы `GET/POST/PUT/PATCH/DELETE/OPTIONS`. Прокси в `vite.config` настраивать
не нужно, обращайся к API напрямую.

## Два важных предупреждения

**1. Сервер работает по HTTP, без TLS.** Пока фронтенд крутится на
`http://localhost:5173`, всё в порядке. Но если ты задеплоишь фронтенд на
HTTPS-домен, браузер заблокирует запросы к `http://` как mixed content, и
приложение перестанет работать. Не полагайся на HTTPS-адрес этого сервера:
по `https://188.94.158.71` API не отвечает. Когда дойдёт до деплоя фронтенда,
этот вопрос нужно поднять отдельно — его решает владелец бэкенда.

**2. Учётной записи на тестовом сервере пока нет.** Демо-аккаунт `sales_demo`
существовал только в локальной базе разработчика, на тестовом сервере его
нет — попытка входа вернёт 401. Запроси у владельца бэкенда учётку: он заводит
её в Django Admin (раздел «Пользователи сервиса продаж»), назначает парки,
услуги и права. Пока аккаунта нет, экран входа и обработку 401 можно проверять,
а всё остальное — нет.

## Чего на этом сервере для тебя нет

Эндпоинт `GET /api/v1/reports/sales/` предназначен для Power BI и отдаёт
продажи **всех** арендодателей. Фронтенду он не нужен и недоступен: у обычной
учётной записи арендодателя он вернёт 403. Используй только `/api/v1/sales/*`.

## Про города и валюту

Напоминание из раздела выше остаётся в силе: определяй валюту по городу парка
(Ташкент — сумы, остальные — тенге) и обязательно обрабатывай случай, когда
`city_name` приходит пустой строкой или `null` — тогда показывай тенге и не
роняй интерфейс. На тестовом сервере база отличается от локальной, так что
проверь на реальных данных, что именно приходит в этом поле.
